# Plan: Grafana compute pool metrics

Date: 2026-11-20
Scope: `Calycopis-broker` — Spring Boot broker metrics, Podman pod monitoring deployment, tests and documentation. No OpenAPI schema, generated client, database migration or public REST API changes.
Issue:
 * [uksrc/Calycopis-broker#231](https://github.com/uksrc/Calycopis-broker/issues/231) — Add Grafana compatible metrics for resource pools.
Branch: `20261120-zrq-grafana-compute-pool-metrics`, created from `main` at `99727d6f`.

## Problem

The broker has no Prometheus registry and no operational metrics for its compute
pools. Its actuator exposes only `health`, `info` and `metrics`, so there is no
time series of how much capacity each pool has allocated, how much live
reservations hold, or how much is available. The pod deployment starts only the
broker and its PostgreSQL database, with no Grafana dashboard.

Issue #231 asks for Prometheus-format metrics for the three capacity states,
a Grafana container in the service deployment, and a dashboard showing them.

## Decisions

 * Add a Prometheus registry to the broker and expose `/actuator/prometheus`.
   The registry supplies the exposition; Prometheus supplies the time dimension.
   The broker keeps no metric history.
 * Compute the metrics in one raw SQL query rather than walking JPA entities.
   The booking query and the allocation over-commit guard already work this way,
   and a pool can hold many reservations. The query follows their block and hull
   rules exactly.
 * Expose two gauges per pool and state, labelled by pool name, pool UUID and
   state:
   * `calycopis_compute_pool_cores`, in cores;
   * `calycopis_compute_pool_memory_bytes`, in bytes.
 * Internal allocation and reservation memory is GiB. The publisher converts it
   to bytes with `1_073_741_824`, so Grafana can format the panels with its
   standard byte units. This also matches the Docker platform's memory
   conversion.
 * Available is allocated minus reserved, and is not clamped. A negative value
   exposes an over-committed pool, which is useful for alerting.
 * Refresh the gauges on a fixed delay, 15 seconds by default, through
   `calycopis.broker.metrics.pool-refresh-milliseconds`. A refresh before
   `MeterBinder.bindTo()` is a no-op; a query failure logs a warning and keeps
   the previous snapshot; gauges for pools that disappear are removed.
 * The deployment gains both Prometheus and Grafana. Grafana cannot query a raw
   exposition endpoint directly, so Prometheus is the scrape/store layer and
   Grafana uses it as a provisioned datasource.
 * Use the current pod deployment in `bin/deploy-broker.sh`, not the superseded
   compose stack. The compose file remains unchanged.
 * Keep the monitoring config in a named volume, generated by
   `bin/config-monitoring.sh` from templates under `docker/monitoring/`. The
   Grafana provisioning path is
   `/etc/calycopis-monitoring/grafana/provisioning`; the dashboard provider
   points at `/etc/calycopis-monitoring/grafana/dashboards`.
 * The Grafana admin password is generated into `grafanapassword` and read with
   `GF_SECURITY_ADMIN_PASSWORD__FILE`, so it never appears in the container
   environment. Sign-up and anonymous access are disabled.
 * Pin `docker.io/prom/prometheus:v3.16.0` and
   `docker.io/grafana/grafana:13.2.6`.

## Metric contract

| Metric | Type | Labels | Unit |
|---|---|---|---|
| `calycopis_compute_pool_cores` | gauge | `pool`, `pool_uuid`, `state` | cores |
| `calycopis_compute_pool_memory_bytes` | gauge | `pool`, `pool_uuid`, `state` | bytes |

`state` is `allocated`, `reserved` or `available`. Values are evaluated for the
60-second block containing the refresh instant:

 * allocated — the sum of the pool's allocation cores/memory whose windows
   cover the block. An open-ended allocation covers every block from its start.
 * reserved — the sum of `COALESCE(maxoffered*, maxrequested*)` over compute
   reservations whose owning session is live (the same phase set as the booking
   query) and whose preparing/available/releasing hull covers the block.
 * available — allocated minus reserved, unclamped.

## Changes

### Broker

 * `java/pom.xml` — add `io.micrometer:micrometer-registry-prometheus`.
 * `java/src/main/resources/application.yaml` — expose `prometheus`; add
   `calycopis.broker.metrics.pool-refresh-milliseconds: 15000`.
 * `engine/functional/metrics/ComputePoolMetricsQuery.java` — the raw SQL and
   `build(Instant)`, substituting `:blockstep` and `:blockstart` as literals.
 * `engine/functional/metrics/ComputePoolMetricsRow.java` — one row per pool,
   memory in GiB.
 * `engine/functional/metrics/ComputePoolMetricsQueryHandler.java` — query
   handler interface.
 * `spring/metrics/SpringComputePoolMetricsQueryHandlerImpl.java` — `JdbcTemplate`
   row mapper.
 * `spring/metrics/ComputePoolMetricsPublisher.java` — `MeterBinder` plus
   `@Scheduled` refresh, gauge reconciliation, byte conversion and failure
   handling.

### Deployment

 * `docker/monitoring/prometheus/prometheus.yml` — scrape template with
   `__BROKER_TARGET__`, 15-second interval.
 * `docker/monitoring/grafana/provisioning/datasources/prometheus.yml` —
   datasource template with `__PROMETHEUS_URL__` and fixed uid
   `calycopis-prometheus`.
 * `docker/monitoring/grafana/provisioning/dashboards/calycopis.yml` — file
   provider for the `Calycopis` folder and the dashboard directory.
 * `docker/monitoring/grafana/dashboards/calycopis-compute-pools.json` —
   dashboard uid `calycopis-compute-pools`, six time-series panels, pool
   template variable, 30-second refresh and six-hour default range.
 * `bin/config-monitoring.sh` — generate the scrape config and datasource,
   copy the dashboard/provider, generate the admin password, set permissions.
 * `calycopis.vars` — monitoring config path/volume, Prometheus and Grafana
   hostnames, container names, images, ports, data paths/volumes and retention.
 * `bin/deploy-broker.sh` — publish the Grafana and Prometheus ports; run the
   config script; start Prometheus and Grafana; wait for `/-/ready` and
   `/api/health`; report the endpoints and password location.

The dashboard JSON cannot carry a comment licence header, because JSON has no
comments. Its authorship is recorded in this plan, the commit and the deployment
guide.

### Tests

 * Java `ComputePoolMetricsQueryTest` — constant exists, block substitution,
   pool/allocation/reservation sources, live phases, offered-then-requested
   sizes.
 * Java `ComputePoolMetricsPublisherTest` — gauge registration and values, byte
   conversion, negative available, stale gauge removal, refresh before bind,
   failure keeps the previous snapshot, refresh updates rather than duplicates.
 * Python `tests/python/any/test_actuator_metrics.py` — read the endpoint, parse
   the exposition, create an isolated `metrics-pool-` pool with a known
   allocation, poll for the refresh, and assert the allocated, reserved and
   available cores and bytes.
 * `tests/python/conftest.py` — add `metrics-pool-` to
   `TEST_POOL_NAME_PREFIXES` so the test pool is disarmed.

### Documentation

 * `docs/deployment.md` — monitoring architecture, metric contract, config and
   password retrieval, verification commands, dashboard description and demo
   notes.
 * `AGENTS.md` — directory layout, a compute-pool metrics paragraph, and the
   new Python test row.
 * `demo/README.md` — monitoring containers, volumes, per-node override
   variables and distinct external ports.
