--START--
No, running rsync inside the container would not solve this problem, and it would actually make the transfer more complex.

The warning symlink has no referent is expected behavior and is not an error. It means rsync correctly identified that the symlink points to a target that does not exist on the host filesystem. Since your DSH_HOME contains symlinks pointing to files that only exist inside the container's filesystem (like node_modules dependencies), these links are "broken" from the host's perspective
....
....
When you mount the transferred DSH_HOME into the container on your laptop, the symlinks will work again because the container provides the missing target files. The host filesystem seeing them as "broken" is not a problem for the container's operation.

#[root@calycopis-dsh]

Follow-up: interacted with the live brokers directly using the endpoint URLs
in `demo/build/hosts.yaml` (http://10.89.x.2:8082, reachable from the DSH
pod network).

## Identities did not match users.yaml

The demo identities in each broker database held the passwords generated in
session 20260924-01, while `demo/build/users.yaml` (and this session's notes)
record newer passwords.  The user creation in `bin/config-users.sh` returns
409 for existing usernames, which the script swallows silently, so re-running
the deployment over existing database volumes keeps the old credentials.

Aligned the live identities with `demo/build/users.yaml` by updating the
BCrypt password hashes in each broker database:

    UPDATE identities SET password_hash = ... WHERE username IN (...);

All four demo users now authenticate on all four brokers (303 on POST
/requests).  Old hashes were recorded in the session transcript.

## Image digest probe cannot surface a digest

The broker only reports a digest mismatch when the image is already in its
local Docker cache, and the client-facing warning message contains the image
name, not the digest.  The probe-based resolution therefore cannot discover a
digest.  Pinned `alpine:3.23` with the known digest
`sha256:85fe1e81d6758c208f3e1eed4338a1997e19d4be002d4dd32d3100c9a8c010a0`
(verified by `podman pull docker.io/library/alpine:3.23`); `resolve_digest`
now returns the known digest for this image without querying the broker, and
the demo tools pass it explicitly.

## metrics.yaml is not imported by the broker

`java/src/main/resources/application.yaml` imports admin.yaml, database.yaml,
spring.yaml and timings.yaml from `/etc/calycopis`, but not metrics.yaml, so
every broker used the default costs-and-metrics values and the per-broker
profiles had no effect.  Added

    - optional:file:/etc/calycopis/metrics.yaml

to the `spring.config.import` list.  Requires a broker image rebuild and
redeploy to take effect on the live brokers.

## Connector results verified live

`bin/broker compare` renders the 4-broker table; `bin/broker accept` and
`bin/broker monitor` report stdout/stderr fetched through the session
connectors (status FINISHED, HTTP GET locations), e.g.

    Output:
    hello-out
    Stderr:
    hello-err

`bin/broker status` passes 4/4 and `demo/bin/smoke-test.py` passes all
brokers.

## config-users.sh now handles existing users

`bin/config-users.sh` now inspects the HTTP response of the
`POST /admin/identities` call: 201 reports the user as created, 409 reports
"already exists (kept existing credentials)" instead of failing silently, and
other codes print the response body.  Verified live against broker alpha
(409 for alice, 201 for a temporary check user, which was then removed).
