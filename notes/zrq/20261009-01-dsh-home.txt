    Target:

        Give the DSH harness home its own volume mount, separate from the
        Lithosia project source mount, so a container can have either one
        without the other.

    Result:

        Work in progress - the Lithosia side is handed over as a patch.

# -----------------------------------------------------
# Why.
#[root@lithosia-dsh-pod]

    DSH_HOME pointed at /Zarquan/lithosia-quadra/dsh, a path *inside* the
    source mount. The harness state was therefore reachable only as a
    subdirectory of the project source, so an agent container had to mount the
    whole source tree to get its own configuration, and the source mount had
    to be read-write for the harness to persist anything. One mount was doing
    two jobs.

    After the change:

        LITHOSIA_CODE   the project source, /Zarquan/lithosia-quadra
        DSH_HOME        the harness home, /opt/dsh, from ${LITHOSIA_CODE}/dsh

    The host state does not move, so no profile, session or credential is
    touched; only the mount point changes. Three variants become possible:
    source only, harness only, or both.

    the Calycopis project links to it. The Lithosia clone is mounted read-only

    The two that matter:

        The inode check proves both paths are one host directory, so the state
        is not a copy and nothing was migrated.

        The session log mtime matching the current time, and the log growing,
        proves the harness is writing into the mounted home. That is the
        property the whole arrangement depends on.

    The check that fails, and why it is not a fault:

        touch /opt/dsh/.sandbox-probe
        touch: cannot touch '/opt/dsh/.sandbox-probe': Permission denied

    That is the DSH file sandbox, not the mount. Under the `workspace-write`
    policy the writable roots are the session workspace (/Calycopis here) plus
    /tmp and the per-user temporary directory, and nothing else:

        writableRoots(policy) = [ policy.workspaceRoot, "/tmp", tmpdir() ]

        @deepseek-ai/dsh-sandbox, lib/index.js

    So an agent whose workspace is a project cannot write DSH_HOME however it is
    mounted, and a denial there says nothing about the volume. The harness
    itself is not confined this way, which is why it can persist sessions while
    the agent's own shell cannot write the same directory. Do not widen the
    workspace to include DSH_HOME to make such a test pass; if a direct write is
    ever needed, use the bash tool's sandbox_permissions escalation and let the
    user approve that one command.

    Still to check, on the host:

        harness only variant    the DSH_HOME mount with no LITHOSIA_CODE mount.
                                The mechanism is proven, the reduced variant is
                                not.
        source only variant     the LITHOSIA_CODE mount with no DSH_HOME.
        a fresh home            init-dsh.sh against an empty DSH_HOME, which is
                                what a new user does first.

    Do not test any of these by launching containers from inside the DSH
    container. Doing that through the mounted Podman socket destabilised the
    session container twice on 2026-10-09 and it needed restarting both times.
# -----------------------------------------------------
# Caveats.
#[root@lithosia-dsh-pod]

    a. The pnpm workspace state file under profiles/web/node_modules records the
       absolute profile path. init-dsh.sh rewrites it; if a plugin install
       misbehaves after the move, run /usr/local/bin/init-dsh.sh again.

    b. Historical manifests under dsh/backups/ name the old path. They are
       records, not configuration.

    c. One harness home, one running harness. Two containers sharing a home will
       corrupt session state; the separate mount makes per-agent homes easy
       (dsh-<name>).

    d. /opt/dsh holds an empty pnpm/store directory in the image. The mount
       shadows it, which is harmless.

    e. VOLUME /root/.dsh in the Dockerfile is legacy and unused whenever
       DSH_HOME is set. Left alone deliberately, to avoid an image rebuild.

+## Running the container
+
+The harness runs in a container built from `docker/Dockerfile`. Two things are
+mounted separately, so a container can have either one without the other:
+
+ * **The project source**, pointed to by `LITHOSIA_CODE` and mounted at
+   `/Zarquan/lithosia-quadra`. Needed to read or edit this project.
+ * **The harness home**, pointed to by `DSH_HOME` and mounted at `/opt/dsh`.
+   This is the harness's single root for user data: profiles, installed
+   plugins, session logs, credentials and backups. The host copy lives in
+   `dsh/`, which `.gitignore` excludes.
+
+| Variable | Container path | Host source | Purpose |
+|---|---|---|---|
+| `LITHOSIA_CODE` | `/Zarquan/lithosia-quadra` | this clone | The project source. |
+| `DSH_HOME` | `/opt/dsh` | `<clone>/dsh` | The harness home. |
+
+### Launch variants
+
+Both mounts, for an agent that can also edit this project:
+
+```bash
+podman run \
+    --rm \
+    --tty \
+    --interactive \
+    --pod    "lithosia-dsh-pod" \
+    --name   "lithosia-dsh-container" \
+    --env    "CONTAINER_HOST=unix:///run/podman/podman.sock" \
+    --volume "${HOST_CONTAINER_PATH}:/run/podman/podman.sock:rw,Z" \
+    --env    "LITHOSIA_CODE=/Zarquan/lithosia-quadra" \
+    --volume "${LITHOSIA_CODE:?}:/Zarquan/lithosia-quadra:rw,Z" \
+    --env    "DSH_HOME=/opt/dsh" \
+    --volume "${LITHOSIA_CODE:?}/dsh:/opt/dsh:rw,Z" \
+    localhost/zarquan/lithosia-quadra:latest \
+        bash
+```
+
+Source only, to read or edit this project with no harness:
+
+```bash
+podman run \
+    ....
+    --env    "LITHOSIA_CODE=/Zarquan/lithosia-quadra" \
+    --volume "${LITHOSIA_CODE:?}:/Zarquan/lithosia-quadra:rw,Z" \
+    ....
+```
+
+Harness only, to run the agent against other mounted projects with no copy of
+this project's source:
+
+```bash
+podman run \
+    ....
+    --env    "DSH_HOME=/opt/dsh" \
+    --volume "${LITHOSIA_CODE:?}/dsh:/opt/dsh:rw,Z" \
+    ....
+```
+
+### Notes
+
+ * The harness home has to be mounted. Without it `DSH_HOME` resolves to a path
+   inside the container's own filesystem, so every profile, plugin and session is
+   lost when the container is removed.
+ * Only one container should use a given harness home at a time. Two harnesses
+   writing the same session state corrupt it. For parallel agents give each its
+   own home, for example `--volume "${LITHOSIA_CODE:?}/dsh-<name>:/opt/dsh:rw,Z"`.
+ * The `:rw,Z` suffix matters: `Z` relabels the mount for SELinux, and without
+   write access the harness cannot persist anything.
+ * On a fresh home the web proxy plugin has to be installed once. The image runs
+   `init-dsh.sh` at build time, but `DSH_HOME` is unset during the build, so that
+   installs into the harness's *default* home rather than the mounted one. Run it
+   again inside the container:
+
+   ```bash
+   /usr/local/bin/init-dsh.sh
+   ```
+
+   It is idempotent — it reinstalls the plugin and reapplies the
+   `dsh-client-connection` patch, both against the mounted home. Then start the
+   harness with `dsh web --no-open`. The Web UI listens on 3080 inside the
+   container, and the proxy plugin publishes 3081.
+
+ * `VOLUME /root/.dsh` in the image is a leftover from when the harness used
+   DSH's default home. It is unused whenever `DSH_HOME` is set, and it creates an
+   empty anonymous volume on every run.
+ * Nothing here is DSH-specific in principle: another harness would get its own
+   variable and its own mount, and a project would choose which to mount.

+    policy the writable roots are the session workspace (/Calycopis here) plus
+    /tmp and the per-user temporary directory, and nothing else:
+
+        writableRoots(policy) = [ policy.workspaceRoot, "/tmp", tmpdir() ]
+
+        @deepseek-ai/dsh-sandbox, lib/index.js
+
+    So an agent whose workspace is a project cannot write DSH_HOME however it is
+    mounted, and a denial there says nothing about the volume. The harness
+    itself is not confined this way, which is why it can persist sessions while
+    the agent's own shell cannot write the same directory. Do not widen the
+    workspace to include DSH_HOME to make such a test pass; if a direct write is
+    ever needed, use the bash tool's sandbox_permissions escalation and let the
+    user approve that one command.
+
+    Still to check, on the host:
+
+        harness only variant    the DSH_HOME mount with no LITHOSIA_CODE mount.
+                                The mechanism is proven, the reduced variant is
+                                not.
+        source only variant     the LITHOSIA_CODE mount with no DSH_HOME.
+        a fresh home            init-dsh.sh against an empty DSH_HOME, which is
+                                what a new user does first.
+
+    Do not test any of these by launching containers from inside the DSH
+    container. Doing that through the mounted Podman socket destabilised the
+    session container twice on 2026-10-09 and it needed restarting both times.
+# -----------------------------------------------------
+# Caveats worth knowing.
+#[root@lithosia-dsh-pod]
+
+    a. The pnpm workspace state file under profiles/web/node_modules records
+       the absolute profile path. init-dsh.sh rewrites it; if a plugin install
+       misbehaves after the move, run /usr/local/bin/init-dsh.sh again.
+
+    b. Historical manifests under dsh/backups/ name the old path. They are
+       records, not configuration.
+
+    c. One harness home, one running harness. Two containers sharing a home
+       will corrupt session state; the separate mount makes per-agent homes
+       easy (dsh-<name>).
+
+    d. /opt/dsh currently holds an empty pnpm/store directory in the image.
+       The mount shadows it, which is harmless.
+
