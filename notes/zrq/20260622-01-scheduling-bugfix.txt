    >     Here's a comprehensive picture of how the processing lifecycle and timing values work together:
    >   
    >     ────────────────────────────────────────
    >   
    >     Processing Request State Transitions
    >   
    >     The Processing Loop
    >   
    >     The broker runs a scheduling loop every 1 second (@Scheduled(fixedDelay = 1000)). Each iteration follows a
    >     three-phase transaction pattern:
    >   
    >     1. getNext() — claim the next pending request (in its own transaction)
    >     2. preProcess() — read the component/session state, decide what to do, return a ProcessingAction (in its own
    >        transaction)
    >     3. action.process() — execute the action outside any transaction (Docker API calls, downloads, etc.)
    >     4. postProcess() — record results, reschedule or advance phase (in its own transaction)
    >   
    >     This design ensures long-running external operations (container creation, data downloads) don't hold database
    >     locks.
    >   
    >     Request Class Hierarchy
    >   
    >     ProcessingRequestEntity (abstract)
    >       ├── SessionProcessingRequestEntity (abstract)
    >       │     ├── PrepareSessionRequestEntity    (ACCEPTED/WAITING → PREPARING)
    >       │     ├── UpdateSessionRequestEntity     (aggregates component phases → session phase)
    >       │     └── ReleaseSessionRequestEntity    (→ RELEASING)
    >       └── ComponentProcessingRequestEntity (abstract)
    >             ├── PrepareComponentRequestEntity  (INITIALIZING/WAITING → PREPARING → AVAILABLE)
    >             ├── MonitorComponentRequestEntity  (monitors AVAILABLE/RUNNING components)
    >             ├── ReleaseComponentRequestEntity  (→ RELEASING → COMPLETED)
    >             └── FailComponentRequestEntity     (→ FAILED)
    >   
    >     Session Lifecycle Flow
    >   
    >     ACCEPTED → WAITING → PREPARING → AVAILABLE → RUNNING → RELEASING → COMPLETED
    >                                                                       ↗
    >                               (any component fails) → FAILED → RELEASING
    >   
    >     1. PrepareSessionRequestEntity handles ACCEPTED → checks if prepareStartInstant is in the future. If yes →
    >        WAITING (reschedules with halving delay). If no → PREPARING, and spawns a PrepareComponentRequestEntity for
    >        every component (executable, compute, storage, data) concurrently.
    >   
    >     2. PrepareComponentRequestEntity handles each component independently — checks the component's own
    >        prepareStartInstant, waits or executes getPrepareAction().
    >   
    >     3. UpdateSessionRequestEntity is the aggregation point — when any component changes phase, it creates an
    >        UpdateSessionRequest. That request counts all components by phase: if all are AVAILABLE → session becomes
    >        AVAILABLE; if any FAILED → session becomes FAILED.
    >   
    >     ────────────────────────────────────────
    >   
    >     The Role of Timing Values
    >   
    >     What Each Value Means
    >   
    >     ┌─────────────────────────────┬───────────────────────────────────────────────────────────────────────────────────┐
    >     │ Field                       │ Meaning                                                                           │
    >     ├─────────────────────────────┼───────────────────────────────────────────────────────────────────────────────────┤
    >     │ prepareStartInstantSeconds  │ Epoch second when preparation may begin                                           │
    >     ├─────────────────────────────┼───────────────────────────────────────────────────────────────────────────────────┤
    >     │ prepareDurationSeconds      │ Expected preparation duration (used to compute available start)                   │
    >     ├─────────────────────────────┼───────────────────────────────────────────────────────────────────────────────────┤
    >     │ availableStartInstantSecond │ Epoch second when the component becomes available (= prepareStart +               │
    >     │ s                           │ prepareDuration)                                                                  │
    >     ├─────────────────────────────┼───────────────────────────────────────────────────────────────────────────────────┤
    >     │ availableStartDurationSecon │ Width of the "start window" (currently always 0)                                  │
    >     │ ds                          │                                                                                   │
    >     ├─────────────────────────────┼───────────────────────────────────────────────────────────────────────────────────┤
    >     │ availableDurationSeconds    │ How long the component remains available before release                           │
    >     └─────────────────────────────┴───────────────────────────────────────────────────────────────────────────────────┘
    >   
    >     Timeline per Component
    >   
    >     |--- PREPARING ---|--- AVAILABLE ---|--- RELEASING ---|
    >     ^                 ^                                   ^
    >     prepareStart      availableStart                      releaseStart
    >   
    >     How Components Chain Their Timing (Set During Offer Creation)
    >   
    >     This is the critical part — the dependency chain is encoded at offer creation time via the timing values:
    >   
    >     Compute:    prepareStart = offer.startInstant - prepareDuration
    >                 availableStart = offer.startInstant
    >     Storage:    prepareStart = session.prepareStartInstantSeconds
    >                 availableStart = prepareStart + prepareDuration
    >     Data:       prepareStart = storage.availableStartInstantSeconds  ← WAITS FOR STORAGE
    >                 availableStart = prepareStart + prepareDuration
    >     Executable: prepareStart = session.prepareStartInstantSeconds
    >                 availableStart = prepareStart + prepareDuration
    >   
    >     How Timing Controls Runtime Decisions
    >   
    >     In PrepareComponentRequestEntity.preProcess():
    >     • If component.getPrepareStartInstant().isAfter(Instant.now()) → phase = WAITING, return no-op
    >     • Otherwise → phase = PREPARING, invoke getPrepareAction()
    >   
    >     When rescheduling in WAITING state, the delay is (prepareStartInstant - now) / 2 — a halving approach that
    >     converges on the start time.
    >   
    >     ────────────────────────────────────────
    >   
    >     The Race Condition Explained by the Timing Model
    >   
    >     The data resource correctly chains: its prepareStartInstantSeconds = storage.availableStartInstantSeconds, so it
    >     won't start downloading until storage is theoretically available.
    >   
    >     However, the compute resource derives its timing from offer.startInstant - prepareDuration — it has no dependency
    >     on storage or data. If the compute resource's prepareStartInstant arrives before storage has actually finished
    >     (because actual preparation took longer than prepareDurationSeconds estimated), compute's getPrepareAction() runs,
    >     finds volume ident [null], and skips the mount.
    >   
    >     The timing model assumes preparation durations are accurate predictions. When they're not (or when all components
    >     share the same prepareStart), the race triggers.

    ?   I would like to change the control mechanism to be based a set of rules that depend on the relationships between the components.
    ?   reducing the effect of the timing values.
    ?   
    ?   * General idea
    ?   
    ?   * The executable should start preparing (downloading the container image) as soon as the session begins preparing.
    ?   * Storage resources should start preparing (creating the volumes) as soon as the session begins preparing.
    ?   * Data resources MUST wait until their corresponding storage resource is ready before they can begin preparing.
    ?   * A compute resource MUST wait until its executable is available, AND all of the storage resources linked to its volume mounts are available before it begins PREPARING.
    ?   * A compute resource MUST wait until its executable, AND all of its storage resources AND all of the data resources linked to its volume mounts are available before it can transition from PREPARING to AVAILABLE and start the container running.
    ?   
    ?   The timing values MAY adjust the times when the transitions happen, making components wait in the WAITING state before they transition to PREPARING and waiting in READY
    ?   before transitioning to AVAILABLE, but the timing values cannot trigger a transition on their own.
    ?   
    ?   The question is where to apply the rules.
    ?   PrepareComponentRequestEntity.preProcess() has the code that checks whether it can go ahead based on the timing values
    ?     • If component.getPrepareStartInstant().isAfter(Instant.now()) → phase = WAITING, return no-op
    ?     • Otherwise → phase = PREPARING, invoke getPrepareAction()
    ?   but PrepareComponentRequestEntity doesn't know or understand what type of component it is dealing with
    ?   so it can't apply transition rules that depend on the type of component.
    ?   
    ?   It looks like the best place to put the rules is in the component entities, but not the final entity classes.
    ?   The rules for compute resources should apply for ALL types of compute resource, and the rules for data resources
    ?   should apply for ALL types of data resource.
    ?   So the best place to define the core rules for the different types of components is probably in the abstract
    ?   base classes for the different types of component, AbstractComputeResourceEntity, AbstractDataResourceEntity etc.

    ?   The existing code in PrepareComponentRequestEntity.preProcess() depends on the current phase of the component,

    ?   The existing code in PrepareComponentRequestEntity.postProcess() compares the previous phase and the

    ?   
    ?   The code in PrepareComponentRequestEntity.postProcess() that decides how long to wait could also be moved

    >     Updated rules:

    >     • Storage: can transition to PREPARING immediately (no dependencies beyond session PREPARING)

    >     DockerSimpleComputeResourceEntity) need the Platform parameter to get the Docker client factory. I'd suggest:
    >

    >             {
    >             return Duration.between(Instant.now(), this.getPrepareStartInstant()).dividedBy(2L);
    >             }
    >         return DEFAULT_RULES_POLL_INTERVAL;
    >         }
